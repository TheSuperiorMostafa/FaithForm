# Group chat and profile image release

Apply `0099_branding_images_and_group_lookup.sql` before deploying the server and iPhone build. This adds the public `branding-images` bucket (JPEG/PNG renditions only), grants no direct client object access, and adds tenant-scoped covering indexes for active group membership lookup. Run the migration through the normal versioned migration runner. Existing church/group images remain readable; no backfill is required.

Group managers can edit the group photo from Group info → Edit group. Church admins can edit church logo/cover from the church profile photo button in the iPhone app or Dashboard → Settings → Church profile images. Platform admins retain their church-profile controls. Upload ownership is derived from authentication; the app never supplies a church ID, storage path, or public image URL. Logo crops are square, covers are 16:9. Uploads are normalized and stripped of metadata, with unique cacheable URLs and compare-and-swap updates to protect concurrent edits. Existing legacy assets are retained when replaced to avoid deleting images shared elsewhere. New owned assets are cleaned up after replacement. Ambiguous storage/database failures retain candidate assets rather than risk deleting a committed image.

The group list's authorized chat summary now opens the conversation immediately. Overview data loads only when requested. Chat connects while the group list is open; the first Stream token comes from the existing session response instead of a duplicate token request. Already synchronized channels are retained only for that in-memory session; sign-out/church/tab teardown clears them. Stream continues enforcing channel membership and posting rules. The existing messaging outbox worker propagates group photo changes to chat channels.

Rehearsal: use `FAITHFORM_TEST_DATABASE_URL` with `scripts/run-groups-database-tests.mjs` against a disposable local PostgreSQL server. This applies the entire migration chain and verifies storage denial and index eligibility with EXPLAIN. Disabling sequential scans in the index test proves eligibility, not a production latency benchmark. Check real devices/network traces before assigning a latency target.

Release smoke checks: upload/crop/replace/remove both church images and a group photo; verify web and iPhone show the new URL; ordinary members must not get edit controls; another church's admin must be refused. Open a joined group cold and warm: the first view must be the chat skeleton or messages, never the overview skeleton. Test keyboard, attachments and returning from group info. Deploying these files or running the storage helper alone does not apply the indexes.
